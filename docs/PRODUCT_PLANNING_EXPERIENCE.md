# 상품기획 부서와 검증 가능한 경험 활용

착수: 2026-10-25 13:52 KST, dev/web-ui @ 5f70f97, clean. 첫 작업은 기존 부서 패키지 형식의 상품기획 부서다.
웹 안정화의 선행 검증은 Python312 읽기/실행 권한과 Chrome 0xC0000022 장애로 계속 보류한다.
동일 환경 진단을 반복하지 않고 runtime-2026-10-25 기록을 유지한다. main 병합/기존 서버 전환 없음.

## 확인한 기존 기능

- departments: 부서별 역할/도구/계약/권한/수용 기준, 프로젝트 연결 이벤트, 실제 CEO 위임, 노트 결과 계약,
  독립 검증의 부서별 기준 판정. 연결된 버전 번호는 있었지만 실행 시 최신 라이브러리를 읽는 공백이 있다.
- research 1.1.0: 제공된 첨부와 앞 단계의 자료 분석. reasoning만 있으며 웹 조사/고객 접촉은 지원하지 않는다.
- operations 1.1.0: 앞 단계의 근거를 사용한 운영 문서·작은 도구. reasoning/code_generation, 네트워크·shell 없음.
- knowledge: 기존 vault 키워드 검색, runtime 검증 실패 카드, SQLite 이벤트의 검색→채택→실행→결과 추적.
- kindex: 기존 검색 평가/FTS5 후보, 최소 표본 미달 시 HOLD. 새 경험 DB나 검색 서버는 만들지 않는다.

## 구현 순서와 경계

1. product-planning 패키지. 고객/문제, 비교, 가치 가설, 손익 시나리오, MVP/제외, 다음 실험.
   조사·자료 정리는 기존 부서의 앞 단계 결과를 사용한다. 제공된 자료가 없으면 미확인으로 표시한다.
   동일 WORK/BUILD 호출 안에서 산출하고 별도 역할마다 모델을 호출하지 않는다.
2. 기존 SQLite events에 검증과 중단의 구조화된 경험 투영을 기록한다. 원본 데이터는 참조 ID로 연결하고 복제하지 않는다.
   자유 텍스트를 cross-project 경험 카드로 복제하지 않는다. 측정값·허용된 분류·원본 참조만 공유한다.
3. knowledge.experience를 확장한다. 프로젝트/부서/시간/검증 수준/적용 조건을 필터하고 필요한 카드만 최대 3개 제공한다.
   문서는 참고 데이터다. 경험의 지시문·실패 사례가 승인·기준을 대체하지 못한다. 검색 없음도 기록한다.
4. A에서 생성한 경험만 B에 허용하는 고정 cutoff와 source-project allowlist로 다른 B 평가 결과 유입을 막는다.
5. 고정 rubric으로 B의 경험 미사용/사용을 비교한다. 실제 실험 전에는 점수·개선율을 만들지 않는다.
6. 모델 학습은 이번 범위에 없다. 프롬프트/규칙/검색의 한계를 비교 검증한 별도 제안 없이는 실행하지 않는다.

부서는 연결 시 명세 스냅샷과 hash를 기존 이벤트에 고정한다. 과거 스냅샷이 없는 프로젝트는 기록된 버전과
라이브러리 버전이 일치할 때만 사용한다. 자동 업그레이드·경험 기반 규칙 변경은 없다.

## 실제 실험 전에 고정할 예산/평가

- 무료·로컬 자료만 사용. CEO가 서로 다른 고객·문제 조건의 작은 과제 A/B를 선택해야 한다.
- 선택도 기존 Engine의 계획·제작·검증·보고를 사용하며 최대 6 agent turns. A/B-control/B-experience 각각 최대 12,
  합계 최대 42 agent turns, provider failover는 기존 최대 2개 CLI(최대 84 attempts, 실제 횟수는 별도 미측정).
- 각 프로젝트 최대 20분, 한 prompt 최대 32,000자, 경험 context 합계 최대 6,000자/3개.
- 토큰은 provider가 실제 보고한 usage만 합산하며 미보고는 UNKNOWN. CLI가 hard token cap을 지원하지 않는 경우
  이를 보장한다고 표시하지 않는다. 토큰 hard cap이 필수인 실행은 지원 여부 확인 전 시작하지 않는다.

`product_experiment.py`는 기존 Engine을 호출하는 실험 드라이버이며 별도 엔진이 아니다. 새 root만 허용하고,
CEO가 세 가지 허구/합성 로컬 데이터 조건 중 A/B를 선택한다. 두 B arm에는 같은 이름·내용의 자료를 제공한다.
최초 rubric/과제/자료/예산/부서 hash를 PRE_REGISTERED.json으로 먼저 고정한다. A의 검증용 텍스트 수정은
Owner-delegated test로 기록하고 REWORK·새 PASS·문구를 포함한 결과 열기를 요구한다. 결과 점수는 별도 보고서에만
보존하며 경험 카드에 넣지 않는다. 실험 budget은 웹/네트워크/설치/프로그램 실행/학습 계획을 거절한다.
토큰 한도는 provider가 보고한 input/output/cache usage의 턴 종료 후 정지 한도다. 한 턴에서 초과 소비하는 것을
사전에 막는 provider hard cap은 **구현되지 않았다**. 미보고 usage는 UNKNOWN으로 두고 후속 호출을 중단한다.
이 제한을 실제 hard cap으로 표시하거나 현 상태에서 실험 완료로 보고하지 않는다.
- 최소 한 과제의 개발자 피드백은 Owner-delegated test input으로 기록하고 실제 Owner 피드백과 구분한다.
- 고정 평가: 근거 정확성, 요구 충족, 구체성/실행 가능성, 손익 계산, 사실/가정 구분 각 0–2점.
  추가로 호출/usage/시간/재작업/개입을 보고한다. 평가 근거가 없으면 UNKNOWN이며 0점으로 대체하지 않는다.
- 같은 B 과제/자료/기준/부서 버전/예산으로 control과 experience를 비교한다. 별도 판정자의 근거와 artifact hash 필요.
- A/B 2과제로 일반적인 품질 향상을 주장하지 않는다. 차이가 없거나 나쁘면 그대로 보고하고 개선안을 적용하지 않는다.
- 개선 후보는 이유/적용 범위/근거/비교 결과/원래 버전을 포함한 별도 기록이다. 부서 버전을 자동 적용하지 않는다.

## 완료 판정

코드/테스트 작성, 로컬 구조 검사, Python 자동 검사, 실제 Engine/CLI 실행, 실제 Chrome, Owner 확인을 구분한다.
부서 카드만으로 완료하지 않는다. 실제 위임·계약·독립 PASS·결과 열기·A 경험·B 선택 이유/차이/채택·평가 기록이 필요하다.
웹 검증 → 보존 빌드 → 실제 실험이 막히면 구현 가능 범위와 미실행을 명시하고 기존 DB/산출물/메모를 보존한다.
